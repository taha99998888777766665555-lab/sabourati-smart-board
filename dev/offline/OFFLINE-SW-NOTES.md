# نسخة تجريبية: العمل دون إنترنت لـ «سبورتي الذكية» (محلي فقط — لم يُرفع ولم يُنشر شيء)

## المحتويات
- `site/` = ما سيوضع في فرع `gh-pages` إن اعتُمد:
  - `board.html` — **ملف السبورة المعتمد دون أي تعديل**، MD5 = `12b8030494f8fe01acbd8d17376ba0c8`.
  - `index.html` — بوابة صغيرة (≈١٫٣ كيلوبايت): تسجّل الـ Service Worker ثم تنتقل إلى `board.html` مرة واحدة (مع الحفاظ على `?…#…`)، وفيها رابط يدوي وبديل `noscript`.
  - `sw.js` — Service Worker محدود بمجلد السبورة (`/sabourati-smart-board/`).
  - `.nojekyll`.
- `tests/offline-sw-test.js` — اختبار آلي (Playwright) بخادم محلي يحاكي ترويسات GitHub (`max-age=600`) ويتحكم في الانقطاع والبطء والبتر.
- `run-logs/` — نتائج التشغيل.

## كيف يعمل
1. **التسجيل:** `index.html` يسجّل `sw.js` بنطاق `./` فقط (لا يستطيع التحكم بـ `/taa11am-ma-taha/`).
2. **التخزين (حزمة ذرّية):** «الحزمة» = `index.html` + `board.html` معًا. عند التثبيت وعند كل تحديث يُنزَّل الملفان ويُتحقق منهما (حالة 200، نوع HTML، علامة داخل الصفحة، حد أدنى للحجم، اكتمال التنزيل)، ثم يُكتبان **في معاملة IndexedDB واحدة (`readwrite`) بمعرّف حزمة `pairId` واحد**. أي استثناء بعد كتابة الأول يُلغي المعاملة كلها (`tx.abort()`)، وأي رفض من IndexedDB (مثل قيد فريد) يُلغيها تلقائيًا. القراءة أيضًا في معاملة قراءة واحدة، وإن اختلف `pairId` بين الملفين أو نقص أحدهما تُعدّ الحزمة غير صالحة ولا يُقدَّم منها شيء.
3. **العزل:** لا يستخدم Cache API إطلاقًا. السبب: Service Worker تطبيق التعلم (الأصلي، دون تعديل) يحذف عند تفعيله **كل** كاش لا يخصه — جرّبته: يحذف كاشًا غريبًا. قاعدة `sabourati-shell-v1` منفصلة عن `sabourati-pro` (رسومات المستخدم وبطاقاته وإعداداته)، ولا يذكر `sw.js` اسم `sabourati-pro` في كوده.
4. **الجلب (للتنقل إلى الملفين فقط):** الشبكة أولًا مع إعادة تحقق (`no-cache`) للحزمة كلها. لا يُسلَّم ملف ولا يُخزَّن شيء قبل نجاح تنزيل الحزمة والتحقق منها وكتابتها. عند الانقطاع أو البتر أو صفحة غريبة (بوابة واي-فاي/404) أو فشل الكتابة أو تجاوز ٣ ثوانٍ تُقدَّم **آخر حزمة مخزَّنة سليمة** كاملة (لا ملف من حزمة وآخر من أخرى). في قفزة البوابة→السبورة تُعاد استخدام الحزمة نفسها فلا يتكرر تنزيل `board.html`. لا يلمس أي طلب آخر.
5. **التحديث:** أي نسخة جديدة من `board.html` تظهر عند أول اتصال وتُخزَّن. تغيير `sw.js` نفسه (رفع `VERSION`) يثبّت Worker جديدًا بانتظار إغلاق التبويبات (لا `skipWaiting` ولا `clients.claim`، فلا يتبدّل الكود في منتصف حصة).

## أثر ذلك على البصمات
- `board.html` (المعتمد): **لم يتغير** `12b8030494f8fe01acbd8d17376ba0c8`.
- `index.html` جديد كليًا (بوابة)، وبه `sw.js` ملفان جديدان؛ بصماتهما تُسجَّل في التقرير النهائي عند الاعتماد.

## ما تغيّر في السلوك الظاهر للمستخدم
- الرابط الرئيسي يمرّ بالبوابة ثم ينتقل إلى `.../board.html` (انتقال سريع).
- لا يتغير تصميم السبورة ولا أدواتها ولا محتواها.

## حدود وقيود صريحة
- **أول زيارة:** يجب فتح الرابط الرئيسي مرة واحدة متصلًا حتى يكتمل التخزين. فتح `board.html` مباشرة لأول مرة لا يسجّل الـ SW (التسجيل في البوابة فقط) فلا يعمل دون إنترنت قبل زيارة الرابط الرئيسي مرة.
- البوابة تنتظر جاهزية الـ SW حتى ٢٫٥ ثانية ثم تنتقل؛ على شبكة بطيئة جدًا يستمر التثبيت في الخلفية، ويفشل إن أُغلق المتصفح قبل اكتماله.
- النسخة المخزَّنة تُقدَّم إن تأخرت الشبكة أكثر من ٣ ثوانٍ، وتُحدَّث للزيارة التالية.
- الحفظ التلقائي للسبورة نفسها (غير مرتبط بالـ SW): بعد إعادة التحميل تبدأ السبورة فارغة وتعرض رسالة «استعادته» لمدة ٢٠ ثانية؛ الاستعادة اليدوية تعمل دون إنترنت أيضًا (مُختبَر).
- المتصفحات قد تُخلي التخزين عند امتلاء الجهاز أو (Safari) بعد فترة من عدم الاستخدام؛ وعندها تحتاج زيارة متصلة لإعادة التخزين.
- مُختبَر على Chromium محاكيًا فقط، **لا** على GitHub الحقيقي ولا Firefox/Safari ولا شاشة Riotouch.
